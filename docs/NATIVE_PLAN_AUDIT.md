## Which requirements apply

The October 10 notebook decision in `MASTER_PLAN.md` and `NOTEBOOK_DESIGN.md` supersedes automatic manuscript saving, within-window splits, split-pane drag targets and the previous continuous whole-book editor layout. Manual Save / Discard / Cancel, ordinary page replacement, detachable tabs and additional windows are the active requirements. Automatic checkpoint parking/resume remains an engine capability rather than a current native interface promise. The original Android, remote Android jobs and physical two-device release gates remain deferred; they are not missing work for this desktop continuation. New services, model/download installation, system settings and opening network access still require separate authorization.

Historical “Done” rows in `PROJECT_STATE.md`, and implemented workflows in the retained guides, qualify React/Tauri and earlier package probes only. The leading native state and `RUST_PORT.md` are the applicable coverage claims. The old 72 ms giant-paragraph measurement is not a native desktop performance result.

## Correctness findings requiring separate slices

1. **Planning semantic validation was frontend-dependent.** The original `workspace.rs::validate_data("planning")` bounded only core arrays, allowing the native generic Save to bypass retained authoring rules. Current continuation adds `crates/storage/src/planning_validation.rs` compatibility/author-transition/conflict-resolution checks for optional reveal/knowledge collections: new knowledge requires a retained character/fact, author source, supported stance/scope and exact current snapshot; `knows` requires approved canon. Unchanged historical stale/partial entries remain preserved. Backend wiring and transaction/archive/conflict regressions passed; unchanged historical claims remain compatible. New/changed explicit event-time transition validation now refuses reversed/nonfinite/invalid relative times; unchanged historical time remains preserved. General fact/status/board/constraint core validation and complete feasibility remain separate work.
2. **Semantic dependency preview is absent.** Editing a fact/time through generic fields gives no authored-ripple review. Deleting a fact can leave reveal/knowledge dependencies dangling. The interface must preview dependents and require explicit link resolution, without changing missing data into inferred canon or silently cascading deletes.
3. **Reference summaries and knowledge scope cannot be substituted with prose inference.** A native reference implementation must label unknown/cyclic/contradictory times and scene-spanning boundary ambiguity; use explicit links and retained frozen facts. It must not search manuscript names or infer a character's presence.
4. **Canvas label and identity gaps were fixed.** Real Pango captions/connections and archive/branch/sync card-reference regressions passed. Card IDs remain board identities even when colliding with a scene ID.
5. **Historical completion claims are easy to misread.** Native coverage summaries should explicitly mention references/dictionaries/knowledge-authoring gaps in addition to the existing parity list. This audit does not erase the retained implementation or its evidence. Source test passes must not imply installed payload or physical-device qualification.

## Recoverable backend planning-validation proposal

Keep schema 1 and immutable revision history. Separate compatibility validation of saved historical payloads from validation of a newly authored transition; loading an old stale snapshot must not rewrite or discard it. Every path that writes/imports/resolves/recovers planning must share the appropriate compatibility checks rather than relying on a JavaScript form.

- Add a typed Rust validator for collection/object/string/numeric bounds, stable unique IDs, supported variants, canonical record/fact/event/plot/board/lane references, reveal target XOR/nonnegative position and valid authored scene scopes. Existing legacy optional `readerReveals` / `knowledge` absence remains valid. Missing external scene evidence needs an explicit compatibility policy rather than deleting it.
- Make new/changed knowledge an author action: validate a character, retained fact, nonempty author source, valid scope, stance and required belief interpretation; freeze exact subject/property/value from the captured fact head in the same expected-parent transaction. `knows` requires approved `status=fact` canon at that author action. Do not apply that current-approval rule to an unchanged historical entry whose fact later became stale.
- Retain historical `factSnapshot` bytes exactly. An unchanged entry may legitimately differ from current canon; mark it stale in views. A new entry or an explicitly reauthored one must match the approved captured source, and direct snapshot tampering through a generic form should be refused without changing the local draft.
- Before deleting a fact/event/payoff, enumerate retained knowledge/reveal/time/constraint/board/plot dependencies and refuse the change until the author resolves those links. Rename/value changes preserve IDs and require a reviewed ripple snapshot rather than a silent cascade.
- Test valid legacy optional-array absence, exact Arabic/Chinese/combining/private-use values, immutable stale entries surviving canon edits, explicit reauthoring against new canon, invalid approved belief/knows-proposal/reveal target/position, missing dependent target deletion, concurrent head changes, import/branch/recovery compatibility and failed-transaction rollback. No schema migration, data cleanup, automatic canon approval or destructive operation is needed.
